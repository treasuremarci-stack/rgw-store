# Supabase и админка АКС — Stage 1

В этом каталоге подготовлена техническая основа админки, но действующий публичный магазин по-прежнему читает products.json. Эта стадия не импортирует товары и не переключает product.html, страницы категорий, цены или фильтры на Supabase.

## Что применить

1. Создайте проект Supabase самостоятельно и не помещайте его URL/ключи в этот репозиторий.
2. Откройте Supabase Dashboard → SQL Editor.
3. Выполните файл supabase/migrations/202610190001_admin_catalog.sql.
4. В Authentication → Users создайте или пригласите администратора. Публичная регистрация в админке не предусмотрена.
5. В SQL Editor добавьте UUID созданного пользователя в белый список:

~~~sql
insert into public.catalog_admins (user_id)
values ('UUID_ПОЛЬЗОВАТЕЛЯ')
on conflict (user_id) do nothing;
~~~

6. Скопируйте admin/config.example.js в admin/config.js и укажите URL проекта и публичный anon/publishable key из Project Settings → API. Файл admin/config.js игнорируется Git и не должен коммититься с секретами.
7. Откройте /rgw-store/admin/ на GitHub Pages. Для локальной проверки используйте локальный HTTP-сервер, а не file://.

service_role key нельзя помещать в браузер, config.js, GitHub Pages или любой другой клиентский код.

## Что хранится в базе

- catalog_categories — категории и подкатегории.
- catalog_products — стабильный строковый ID, название, бренд, модель, категория, цена в TJS, JSONB-характеристики, основное изображение и статус публикации.
- catalog_product_images — дополнительные изображения и порядок галереи.
- catalog_admins — белый список пользователей Supabase Auth.
- Storage bucket catalog-images — подготовлен для изображений каталога.

Все таблицы имеют RLS. Читать опубликованные данные может публичная часть, а создавать, редактировать и удалять данные могут только аутентифицированные пользователи, присутствующие в catalog_admins. Права дополнительно проверяются базой, а не только интерфейсом.

## Что умеет /admin/

- вход по email и паролю через Supabase Auth;
- таблица товаров с поиском по ID, названию, бренду и модели;
- фильтр по категориям и статусу публикации;
- добавление и редактирование товара;
- изменение цены в сомони;
- редактирование JSONB-характеристик;
- указание путей изображений, загрузка изображений в Storage и управление галереей;
- публикация/скрытие товара;
- создание, редактирование и удаление категорий с подтверждением.

Удаление категории, на которую ссылаются товары, блокируется ограничением внешнего ключа.

## Проверка безопасности

До добавления записи в catalog_admins входящий пользователь не должен получить данные админки или выполнить INSERT/UPDATE/DELETE. Для проверки используйте отдельного тестового пользователя и не используйте service_role в браузере.

На этой стадии публичный сайт не получает данные из Supabase. Поэтому изменения через админку не изменяют текущий каталог, пока отдельным решением не будет выполнен следующий этап миграции и интеграции.

## Проверка исходного каталога перед импортом

Инструмент tools/validate_catalog_import.mjs ничего не удаляет и не изменяет в каталоге. Он анализирует products.json, price.csv, страницы rgw_page_*.html, локальные изображения и, если передан baseline-файл, сохранность ID.

Пример:

~~~bash
node tools/validate_catalog_import.mjs . reports/catalog-import-report.json
~~~

Проверка с ненулевым кодом выхода при ошибках:

~~~bash
node tools/validate_catalog_import.mjs . reports/catalog-import-report.json --strict
~~~

Сравнение с сохраненной предыдущей версией:

~~~bash
node tools/validate_catalog_import.mjs . reports/catalog-import-report.json --baseline-products products.before.json
~~~

Отчет формируется отдельно и не перезаписывает products.json, price.csv или HTML.

## Ограничения Stage 1

Пока не выполняются массовый импорт, синхронизация цен, переключение публичного каталога и автоматическая публикация. Эти действия относятся к следующему этапу и требуют отдельного решения после проверки отчета.
